Attribute lookup

Reading r1.something searches the instance first, then its class. Writing r1.something = … never searches. Those two rules explain a bug that sends one device's config to another.

One new thing: data in the class body

So far, the only lines inside a class body have been def lines. A class body can also hold an ordinary assignment, outside any def:

class ConfigPush:
    commands = []                  # the config lines to send

    def __init__(self, hostname):
        self.hostname = hostname

Lesson 0001 showed that the def lines run once, when Python runs the class statement, and that the methods they make are stored on the class. The line commands = [] runs at the same time and is stored in the same place: one list, stored once, on the class ConfigPush. Two new terms:

class attribute
A name stored on the class: commands above. The methods are class attributes too. The Python tutorial and Think Python call data stored this way a class variable; this course says class attribute.
instance attribute
A name stored on one instance, usually by self.x = … in __init__: hostname above. This is what lessons 0001 and 0002 called simply an attribute, and what vars(r1) shows.

class ConfigPush:

        self.commands.append(line)


r1 = ConfigPush("r1")

Attribute lookup: you saw it in lesson 0001

Lesson 0001 traced r1.describe() like this:

Python looks for describe on r1. It isn't there: r1 holds only its data. So Python looks in r1's class, Device, and finds the method.

That search has a name: attribute lookup. It isn't special to methods. Python does it for every attribute you read, data included:

Reading instance.attr:

  1. Look on the instance. If it has attr, use that.
  2. If not, look in the instance's class. If the class has attr, use that.
  3. If neither has it, stop with AttributeError.

Python's data model, §3.2.11 Class instances: the instance “is the first place in which attribute references are searched. When an attribute is not found there, and the instance's class has an attribute by that name, the search continues with the class attributes.”

In dict-and-function terms, it's like reading a per-device dict that falls back to one shared dict. A simplified model, not Python's actual code:

def read_attribute(instance_attrs: dict, class_attrs: dict, name: str):
    if name in instance_attrs:          # 1. the instance
        return instance_attrs[name]
    if name in class_attrs:             # 2. its class
        return class_attrs[name]
    raise AttributeError(name)          # 3. neither

Back to the bug

Take sw1.add("vlan 10") one step at a time:

  1. Python looks up add: not on sw1, found on ConfigPush. It runs with self = sw1.
  2. self.commands is a read, so Python looks it up: not on sw1, found on ConfigPush. That's the one list stored on the class.
  3. .append("vlan 10") mutates that list.

r1.add(…) took the same steps and found the same list. This is lesson 0002's aliasing again: r1.commands and sw1.commands lead to one object, so r1.commands is sw1.commands is True. Nothing in the class ever created a list for an individual device.

Writing never searches

Assignment to an attribute works differently. instance.attr = value doesn't look anywhere. It always stores attr on the instance itself, even when the class already has an attribute with that name, and it never changes the class.

Data model, §3.2.11: “Attribute assignments and deletions update the instance's dictionary, never a class's dictionary.” (Dictionary here means the instance's own storage, the thing vars() shows. The optional section below says more.)

This matches lesson 0002's test: an attribute on the left of = mutates an object, and that object is whatever is before the dot: here, the instance. After r1.commands = [], r1 has its own commands. Lookup checks the instance first, so from then on r1.commands finds r1's list and never reaches the class's. The class's list, and sw1, are untouched.

So three kinds of line use an attribute name, and they behave differently:

LineWhat Python does
x = sw1.commandsRead. Look up: the instance, then the class.
sw1.commands = []Write. No search: store on sw1 itself.
sw1.commands.append(…)Read, then mutate. Look up commands (the instance, then the class), then change whatever object it found. That's the demo's bug.

What goes where

The rules give the design reason. A class attribute is one object, and every instance reads the same one. That suits things that are the same for every instance and that no instance changes: the methods, and constants such as the highest valid VLAN ID. Data that differs from device to device has to be created for each device, so it belongs on the instance. The procedural version is the same split: a module-level constant such as MAX_VLAN_ID = 4094, and one dict per device.

See it in Python

Don't take this page's word for it. Start python3 and type each line after >>>. One new statement: del r1.commands deletes the attribute commands from the instance r1. This is what it printed when this lesson was written:

>>> class ConfigPush:
...     commands = []
...     def __init__(self, hostname):
...         self.hostname = hostname
...     def add(self, line):
...         self.commands.append(line)
...
>>> r1 = ConfigPush("r1")
>>> vars(r1)                              # only r1's own attributes
{'hostname': 'r1'}
>>> "commands" in vars(ConfigPush)        # commands is stored on the class
True
>>> r1.commands is ConfigPush.commands    # found by lookup: the same list
True
>>> r1.add("vlan 10")
>>> ConfigPush.commands                   # add() mutated the class's list
['vlan 10']
>>> r1.commands = []                      # write: stored on r1
>>> vars(r1)
{'hostname': 'r1', 'commands': []}
>>> ConfigPush.commands                   # the class's list is untouched
['vlan 10']
>>> r1.commands                           # r1's own list is found first
[]
>>> del r1.commands                       # remove r1's own attribute
>>> r1.commands                           # lookup reaches the class again
['vlan 10']
>>> r1.mtu                                # on neither
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
AttributeError: 'ConfigPush' object has no attribute 'mtu'

Note that vars(ConfigPush) works on a class too. Printed in full it lists several entries Python adds itself, which is why the line above only asks whether commands is in it.

Under the hood (layer 3, optional)

Skip this if the layer 2 rules above aren't solid yet. It adds no new behaviour, only where the behaviour lives.

  • Where instance attributes live. An instance of a class like these has a dict holding its own attributes, stored on it as r1.__dict__. vars(r1) simply returns it (vars()): r1.__dict__ is vars(r1) is True.
  • The class has one too, ConfigPush.__dict__, holding commands, __init__ and add. Python won't let you change it directly: ConfigPush.__dict__["x"] = 1 raises TypeError: 'mappingproxy' object does not support item assignment. Write ConfigPush.x = 1 instead.
  • So the rules are dict operations. Reading r1.commands checks r1.__dict__, then type(r1).__dict__, where type(r1) is ConfigPush. Writing r1.commands = [] does r1.__dict__["commands"] = []. That's the read_attribute model above, with the real dicts filled in.

Where “instance first, then its class” is incomplete, so you aren't surprised later. With inheritance, the search continues from the class into its parent classes (route step 5). Some special class attributes, property among them, are checked even before the instance (step 6). And a function found on the class is turned into a bound method on the way out, which is how self gets filled in (step 4). Each gets its own lesson.

Your turn: fix a VLAN planner

Open lessons/code/l0003_switch.py from the Explorer sidebar:

class IosSwitch:
    """One IOS access switch, and the VLANs this run will add to it."""

    max_vlan_id = 4094
    vlans_to_add = []

    def __init__(self, hostname: str) -> None:
        self.hostname = hostname

    def plan_vlan(self, vlan_id: int) -> None:
        if not 1 <= vlan_id <= self.max_vlan_id:
            raise ValueError(f"VLAN ID out of range: {vlan_id}")
        self.vlans_to_add.append(vlan_id)

    def commands(self) -> list[str]:
        return [f"vlan {vlan_id}" for vlan_id in self.vlans_to_add]

After the exercise: both kinds in the real framework

  
Read this once your checks pass. The resource-module framework uses each kind of attribute
    for the job this lesson gave it.

  
Per-run data goes on the instance. ResourceModule is the class
    that every resource module's config class, such as cisco.ios's
    Vlans, is built on (how one class builds on another is route step 5). Its
    __init__ creates a new commands list for each instance
    (resource_module.py, line 52):


        self.commands = []

  
The lines just above it store self.want and self.have the same way.
    Each module run gets its own WANT, HAVE and commands.

  
Shared, read-only data goes on the class. The VLAN template class keeps its
    parsers (each one a regex for reading a config line plus a Jinja template for writing one) as
    a class attribute
    (rm_templates/vlans.py, lines 35–44):


class VlansTemplate(NetworkTemplate):
    def __init__(self, lines=None, module=None):
        ...

    # fmt: off
    PARSERS = [
        {
            "name": "vlan_configuration",
            ...

  
The code that uses it reads self._tmplt.PARSERS
    (network_template.py, line 77).
    There, self._tmplt refers to a VlansTemplate instance. The instance
    has no PARSERS of its own, so lookup finds the class's list. Line 85 then works
    on a deep copy of each parser's result instead of changing it, so the shared list is never
    mutated. (What a deep copy is belongs to the other course.)

  
One honest note: Vlans itself keeps a plain list of parser names on the
    instance, set in __init__
    (vlans.py, line 48).
    Nothing ever changes that list, so a class attribute would have worked too. For data no one
    mutates, both are safe. The rule that matters is the one in the demo: never mutate a class
    attribute through self.
