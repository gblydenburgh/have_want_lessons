Lesson 0001 · Classes from the ground up

What a class is

If you've stored a device in a dict and written functions that work on it, you already know most of what a class is.

About 25 minutes For network engineers who script in Python No previous knowledge of classes needed

Why learn this

Most network-automation scripts get by with dicts and functions, and that's fine. But the larger tools you rely on are written with classes. Ansible's network resource modules are one example: the cisco.ios collection has a class called VlansFacts that gathers VLAN information from a device. To read, fix or extend code like that, you need to know what a class is and how it works. This lesson covers the first step: what a class is, built from code you already write.

Three words first

These general programming terms come up throughout. Here they are, using an ordinary function:

def describe(device):        # device is a parameter
    ...

describe(r1)                 # r1 is the argument
parameter
The name in the def line that receives a value: device.
argument
The value you pass in when you call the function: r1. While the function runs, the parameter device refers to that value.
local variable
A name that exists only while a function runs. Parameters are local variables, and so is any name you assign inside the function. When the function returns, they're gone.

Start with what you know

Here's a device written the way most scripts would write it: a dict, a function that builds the dict, and a function that works on it.

def make_device(hostname, mgmt_ip, platform):
    return {"hostname": hostname, "mgmt_ip": mgmt_ip, "platform": platform}


def describe(device):
    return f"{device['hostname']} ({device['platform']}) at {device['mgmt_ip']}"


r1 = make_device("r1", "10.0.0.1", "ios")
print(describe(r1))

It prints r1 (ios) at 10.0.0.1. For a short script this is the right design, and you shouldn't swap it for a class. As code grows, two things start to hurt:

  • Nothing connects describe to device dicts. You can pass it an interface dict by mistake, and you only find out when it fails with KeyError.
  • The data and the functions that belong to it are kept apart. With device dicts, interface dicts and VLAN dicts in one program, it's up to you to remember which functions go with which kind of dict.

A class solves both by keeping the data and the functions that work on it together.

The same thing as a class

class Device:
    def __init__(self, hostname, mgmt_ip, platform):
        self.hostname = hostname
        self.mgmt_ip = mgmt_ip
        self.platform = platform

    def describe(self):
        return f"{self.hostname} ({self.platform}) at {self.mgmt_ip}"


r1 = Device("r1", "10.0.0.1", "ios")
print(r1.describe())

This also prints r1 (ios) at 10.0.0.1. Each piece of the dict version has a matching piece here:

Dict versionClass versionWhat it's called
(nothing)class Device: A class: the definition of what a device is, like a template. It isn't a device itself.
make_device(...)Device(...) Calling the class creates an instance. Creating one is called instantiating the class.
the dict r1the instance r1 An instance, also called an object: one particular device made from the class.
device["hostname"]r1.hostname An attribute: a named value stored on an instance. It does the job of a dict key, written with a dot.
the body of make_devicedef __init__(self, ...) The initializer: Python runs it automatically on each new instance, to store its starting attributes.
def describe(device)def describe(self), inside the class A method: a function defined inside a class, which works on one instance.
the device parameterthe self parameter self: the instance the method is working on. It does the job your device parameter did.
describe(r1)r1.describe() Calling a method. Python passes r1 in as self for you.

self isn't a special word; it's just the name everyone uses for that first parameter. You could call it anything, but don't: every Python programmer expects self.

Where things are stored

Everything in Device is written inside the class, but not everything is stored there. The class contains two kinds of lines, and they run at different times:

  • The def lines (lines 2 and 7 of the listing) run once, when Python first reads the class. Each one stores a function in the class. From then on, Device holds two methods: __init__ and describe.
  • The self.… = … lines (lines 3–5) are instructions inside __init__. They don't run when Python reads the class. They run each time a new instance is created, and they store values on that instance.

So after lines 11 and 12 have run:

Device (the class)            r1 (an instance)          sw1 (an instance)
  __init__                      hostname: 'r1'            hostname: 'sw1'
  describe                      mgmt_ip:  '10.0.0.1'      mgmt_ip:  '10.0.0.2'
                                platform: 'ios'           platform: 'nxos'

Each instance holds its own data. The methods are stored once, in the class, and every instance shares them. It's the same split as the dict version: each dict held only data, and describe was defined once, outside every dict. The data differs from device to device, so each instance needs its own. The method code is the same for every device, so one copy is enough, and self tells it which device to work on.

What happens, step by step

Line numbers refer to the listing (on the right, or at the top on a narrow screen).

Line 11: r1 = Device("r1", "10.0.0.1", "ios")

  1. Python creates a new, empty instance of Device.
  2. It runs __init__ on it automatically. The parameters receive: self = the new instance, hostname = "r1", mgmt_ip = "10.0.0.1", platform = "ios".
  3. Lines 3–5 store three attributes on the new instance. self.hostname = hostname means: “on this instance, store the value of the parameter hostname under the name hostname”.
  4. __init__ ends. Its parameters, being local variables, are gone, but the attributes stay on the instance. The instance is given the name r1.

Line 12 does the same again and creates a second, separate instance, sw1, with its own three attributes. The class is written once; every Device(...) call makes a new instance.

A note on names: many tutorials call __init__ the “constructor”. It doesn't actually build the instance, though. Python has already created it, and __init__ fills in its attributes. That's why this course says initializer, and Think Python says “the init method”.

Line 13: print(r1.describe())

  1. Python looks for describe on r1. It isn't there: r1 holds only its data. So Python looks in r1's class, Device, and finds the method.
  2. It runs the method with self = r1. In other words, r1.describe() is the same call as Device.describe(r1): Python puts the instance before the dot in as the first argument. This is how the empty parentheses in r1.describe() still supply the one argument describe needs.
  3. Line 8 reads self.hostname, self.platform and self.mgmt_ip. Since self is r1, those are r1's values, and it returns "r1 (ios) at 10.0.0.1".

sw1.describe() runs the same method code with self = sw1 and returns "sw1 (nxos) at 10.0.0.2".

Always write self. inside a method. In describe, a bare hostname would mean a local variable of describe, and there isn't one. Python would stop with NameError: name 'hostname' is not defined. To use the instance's data, write self.hostname.

Your turn: add to the class

A script that logs in to devices needs a login string like netops@10.0.0.1. You'd normally write a function ssh_target(device) for that. Instead, add it to the class. Open lessons/code/l0001_device.py from the Explorer sidebar; it starts as a copy of the example class.

  1. Store a username. Add a fourth parameter, username, to __init__, and store it on the instance as an attribute called username.
  2. Add a method. Add a method ssh_target that returns the username, an @, and the management IP: for example "netops@10.0.0.1". Remember to use self. for both.
  3. Update the example at the bottom of the file: pass a username to Device(...), and print r1.ssh_target().
  4. Check your work: 
    python3 lessons/code/l0001_check.py
    It reports which step passed, or what's wrong. Keep going until it prints “All checks passed.”
