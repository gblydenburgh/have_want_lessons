Lesson 0001 · Classes from the ground up

What a class is

You already write the same thing with a dict and some functions. A class is that, bundled.

About 20 minutes Assumes nothing about classes Ends with code you write

Start with what you know

Here's a device, written the way you'd write it today: a dict, a function that builds it, and a function that works on it.

def make_device(hostname, mgmt_ip, platform):
    return {"hostname": hostname, "mgmt_ip": mgmt_ip, "platform": platform}

def describe(device):
    return f"{device['hostname']} ({device['platform']}) at {device['mgmt_ip']}"


r1 = make_device("r1", "10.0.0.1", "ios")
print(describe(r1))     # r1 (ios) at 10.0.0.1

Nothing wrong with that. For a short script, it's the right choice, and you shouldn't replace it with a class. But notice two things:

  • Nothing ties describe to device dicts. You could pass it an interface dict or a VLAN dict, and you'd only find out when it raised KeyError.
  • The data and the functions that belong to it live apart. In a big codebase with device dicts, interface dicts and VLAN dicts, you have to remember which functions go with which dict.

A class fixes both by keeping the data and its functions together. It matters for the mission because the Ansible resource-module code you want to work in is written this way.

The same thing as a class

What you write today

def make_device(hostname, mgmt_ip, platform):
    return {"hostname": hostname,
            "mgmt_ip": mgmt_ip,
            "platform": platform}

def describe(device):
    return (f"{device['hostname']} "
            f"({device['platform']}) "
            f"at {device['mgmt_ip']}")


r1 = make_device("r1", "10.0.0.1", "ios")
print(describe(r1))

As a class

class Device:
    def __init__(self, hostname, mgmt_ip, platform):
        self.hostname = hostname
        self.mgmt_ip = mgmt_ip
        self.platform = platform

    def describe(self):
        return (f"{self.hostname} "
                f"({self.platform}) "
                f"at {self.mgmt_ip}")


r1 = Device("r1", "10.0.0.1", "ios")
print(r1.describe())

Both print r1 (ios) at 10.0.0.1. Here's how each piece of the left side turns into the right side, and the name for each piece.

Dict and functionsClassWhat it's called

def describe(device)def describe(self), inside the class A method: a function defined inside a class, which works on one instance.
the device parameterthe self parameter self: the instance the method is working on. It plays the role your device parameter played.

That last row is the key to self. The Python tutorial says “the call x.f() is exactly equivalent to MyClass.f(x)” (§9.3.4). So r1.describe() is the same call as Device.describe(r1): your old describe(r1), with the function now living inside the class. And self is just a parameter name; “the name self has absolutely no special meaning to Python” (§9.4). Everyone uses it by convention.

What happens, step by step

The listing on the right (or at the top, on a narrow screen) is the class you'll use from here on. Line numbers refer to it.

Line 11: r1 = Device("r1", "10.0.0.1", "ios")

  1. Python creates a new, empty instance of Device.
  2. It calls __init__ automatically, with self = that new instance, hostname = "r1", mgmt_ip = "10.0.0.1", platform = "ios" (§9.3.2).
  3. Lines 3–5 store three attributes on that instance: self.hostname = hostname means “on this instance, store the value under the name hostname”.
  4. __init__ finishes, and the instance, now holding three attributes, is assigned to the name r1.

Line 12 does the same again and builds a second, separate instance, sw1, with its own three attributes. The class is written once; each call makes a new instance.

A word you'll meet: many tutorials, including the video below, call __init__ the constructor. Python's own reference says __init__ is “called after the instance has been created” (data model), so it doesn't construct the instance. It fills in one that already exists. That's why this course calls it the initializer.

Line 13: print(r1.describe())

  1. r1.describe() calls the method describe, with self = r1.
  2. Line 8 reads self.hostname, self.platform and self.mgmt_ip. Because self is r1, those are r1's values.
  3. It returns "r1 (ios) at 10.0.0.1", and print shows it.

sw1.describe() would run the same method code, with self = sw1, and return "sw1 (nxos) at 10.0.0.2".

Check yourself

Six quick questions about the listing. Pick an answer and you'll see right away whether it's right and why. Only your first pick counts toward the score, but read the explanations for the other options too.

1. After line 11 runs, what is r1?
Right. Calling Device(...) creates a new instance and runs __init__ on it; r1 names that instance.
Not quite. Device is the class, the blueprint. Calling it with Device(...) builds a new instance from it, and that instance is what r1 names. (r1 = Device, without the parentheses, would be the class under another name.)
Not quite. describe isn't called on line 11 at all. Line 11 calls the class, which creates an instance and runs __init__.
2. Line 13 calls r1.describe(). While line 8 runs, what is self?
Not quite. self is never the class in an ordinary method. r1.describe() is the same as Device.describe(r1): r1 is passed in as self.
Right. Python passes the instance before the dot, r1, as the first argument, self.
Not quite. describe is the method that's running; self is the instance it's working on: r1.
3. Which line stores the attribute mgmt_ip on r1?
Not quite. Line 2 only says __init__ takes a parameter called mgmt_ip. A parameter is a local name for the argument; nothing is stored on the instance until line 4 runs.
Right. self.mgmt_ip = mgmt_ip stores the parameter's value on the instance as an attribute. It runs when line 11 calls Device(...).
Not quite. Line 8 reads self.mgmt_ip; it doesn't store anything. The attribute must already exist, or line 8 would fail.
4. r1.describe() is exactly the same call as which of these?
Not quite. There's no function called describe outside the class any more, so this would raise NameError.
Not quite. Python already passes r1 as self, so this passes it twice. describe takes only self, so you'd get a TypeError about too many arguments.
Right. This is the tutorial's “x.f() is exactly equivalent to MyClass.f(x)”: the instance becomes self.
5. After line 12 creates sw1, what is r1.hostname?
Right. Each instance has its own attributes. Creating sw1 ran __init__ on a different instance, so r1 is untouched.
Not quite. Line 12 made a separate instance and stored "sw1" on it. r1 still holds what line 11 stored.
Not quite. hostname is the attribute's name; r1.hostname gives you its value, which is "r1".
6. When does __init__ run?
Not quite. Reading the class only defines its methods. __init__ runs on each new instance, so it runs twice here: line 11 and line 12.
Right. Every Device(...) creates a new instance and runs __init__ on it: twice in this listing, at lines 11 and 12.
Not quite. Calling a method doesn't re-run __init__. describe uses the attributes __init__ already stored.
