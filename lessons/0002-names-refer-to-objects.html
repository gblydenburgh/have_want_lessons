Names refer to objects

Every Python name works like a Perl reference, and Python follows it for you. That's why you never write @{}, and why want = have can wreck a diff.

A bug to start with

You've read a VLAN from a device (HAVE). The task asks for a new name. A natural first draft builds WANT by starting from HAVE and changing the one key, then compares the two to decide whether the device needs a change. The file is lessons/code/l0002_demo.py:

have = {"vlan_id": 10, "name": "users"}   # read from the device
want = have                                # start from what the device has
want["name"] = "staff"                     # apply the task's change

print("HAVE:", have)
print("WANT:", want)
print("Needs a change:", want != have)

This is what it printed when this lesson was written:

HAVE: {'vlan_id': 10, 'name': 'staff'}
WANT: {'vlan_id': 10, 'name': 'staff'}
Needs a change: False

HAVE says staff, though the device still has users. The comparison says nothing needs changing, so a module built this way would report changed: false and leave the device as it is. No error, no warning. Line 2 is the cause, and to see why you need Python's model of names.

Names and objects

A few words first.

object
Any value Python has created: a dict, a list, a string, a number, a Device instance. Each object exists once, in memory, until nothing uses it any more.
name
What you've always called a variable: have, want, r1. A name isn't an object, and it doesn't contain one. It refers to one.
reference
The link from a name to an object. “have refers to the dict” and “have is a reference to the dict” mean the same thing.

Now the two rules everything else follows from (both from Ned Batchelder's talk, backed by the Python reference: “the name is bound to the object”):

1. Assignment makes the name on the left refer to the object on the right.

2. Assignment never copies. If the right side is an object that already exists, the name ends up referring to that same object.

Line 1, have = {"vlan_id": 10, "name": "users"}: the {…} on the right creates a new dict object, and the assignment makes the name have refer to it.

Line 2, want = have: the right side is just the name have, so Python follows it to the dict it refers to, and makes want refer to that same dict. Nothing is copied, and no second dict exists.

Line 3, want["name"] = "staff": Python follows want to the dict and changes the dict. have refers to the same dict, so it sees the change. Then want != have compares a dict with itself, which can only be False.

When two or more names refer to one object, the object is aliased, and each name is an alias (Think Python, §9.10).

Checking it: is and ==

Python has two different questions you can ask about two names:

WriteIt asksTerm
a == bDo the two objects have the same contents?equal
a is bDo both names refer to the very same object? (reference §6.10.3: “x is y is true if and only if x and y are the same object”) identical

After the demo, want is have is True. Two separately built dicts with the same contents are equal but not identical: == gives True, is gives False.

Where Perl's @{} went

Perl has two kinds of variable for a hash. %have is the hash. A scalar like $have_ref holds a reference to a hash, made with a backslash (perlreftut, Make Rule 1). The two behave differently when you assign them:

my %want = %have;             # copies the hash: two separate hashes
$want{name} = 'staff';        # %have still says 'users'

my $have_ref = \%have;
my $want_ref = $have_ref;     # copies the reference: one hash, two references
$want_ref->{name} = 'staff';  # %have now says 'staff'

Checked with Perl 5.38. perlreftut on the second case: “You get two references to the same array.” (perlreftut)

To use what a Perl reference refers to, you dereference it: @{$aref}, %{$href}, or ->. Without that, Perl would treat $have_ref as the reference itself, not the hash. That is what @{} was for.

Python has only the second kind. Every name is like $have_ref: it always holds a reference, never the object itself. Because there's no other kind, Python always follows the reference for you, every time you use the name. There's no choice to make, so there's nothing like @{} to write.

PerlPython
my $want_ref = $have_ref;want = have — one object, two references
$want_ref->{name} = 'staff';want["name"] = "staff" — following the reference is automatic
my %want = %have;No assignment does this. A copy has to be built on purpose.

So the demo's line 2 is Python's version of $want_ref = $have_ref. If you'd read it as %want = %have, the bug is invisible.

Changing an object, or moving a name

Line 3 changed the dict. A different kind of line moves a name instead. The two look similar but do very different things:

KindExamplesWhat happens
mutate (change the object) want["name"] = "staff"
want.update(...)
vlans.append(30)
r1.mgmt_ip = "10.0.0.9"		 The object itself changes. Every name that refers to it sees the change.
rebind (move a name) want = {...} Only that one name changes: it now refers to a different object. Other names, and the object it used to refer to, are untouched.

The test: is there a bare name, and nothing else, on the left of the =? Then it's a rebind. A subscript (want[…]), an attribute (r1.mgmt_ip) or a method call (.append) changes an object.

Here's a rebind after want = have:

have = {"vlan_id": 10, "name": "users"}
want = have
want = {"vlan_id": 10, "name": "staff"}    # a new dict; want now refers to it

Being aliased isn't permanent. Line 2 doesn't link the two names. It just made them refer to the same object for now.

Two corrections to lesson 0001

With this model in place, two sentences in lesson 0001 were imprecise. Lesson 0001 stays as it was; the corrections are here.

  1. “The instance is given the name r1.” That suggests the instance owns a name. It doesn't. Device(...) creates the instance and returns it, and then the assignment makes the name r1 refer to it. The instance doesn't know which names refer to it. After core = r1, two names refer to it. In Device("r9", "10.0.0.9", "ios").describe(), none do. That's also why print(r1) shows <__main__.Device object at 0x…> and no name.
  2. Quiz question 3 said line 3 “copied the value onto the instance”. Nothing is copied. self.hostname = hostname makes the attribute hostname on the instance refer to the same string object the parameter refers to. When __init__ returns, the parameter is gone, but the attribute still refers to the string, so the string stays. Attributes are names too: they refer to objects exactly as have and want do.

Passing an argument is an assignment too

Ned Batchelder: “Function arguments are perhaps the most important thing that doesn't look like an assignment, but is.” When you call a function, Python makes each parameter refer to the object you passed in. So the parameter and your name are aliases of one object while the function runs:

def shutdown(interface):
    interface["enabled"] = False         # mutates the dict that was passed in


gi1 = {"name": "GigabitEthernet0/1", "enabled": True}
shutdown(gi1)
print(gi1["enabled"])                     # False

See it in Python

Don't take this page's word for it. Start Python with python3 and type each line after the >>> prompt. This is what it printed when this lesson was written:

>>> have = {"vlan_id": 10, "name": "users"}
>>> want = have
>>> want is have                  # one object, two names
True
>>> want["name"] = "staff"        # mutate: change the object
>>> have
{'vlan_id': 10, 'name': 'staff'}
>>> want = {"vlan_id": 10, "name": "staff"}   # rebind: a new dict
>>> want is have
False
>>> want == have                  # different objects, same contents
True
>>> name = "r1"
>>> class Device:
...     def __init__(self, hostname):
...         self.hostname = hostname
...
>>> d = Device(name)
>>> d.hostname is name            # the attribute refers to the same string
True
